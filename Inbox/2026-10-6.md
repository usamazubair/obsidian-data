View
## A view is a saved query with a name

That's all it is. Nothing more.

You have a long query you'd otherwise retype every time. You give it a name once, and from then on you use the name.

**Without a view**, every time you want live shops you type this:

```sql
SELECT * FROM shop s
JOIN (SELECT tenant_id, max(last_seen) AS newest FROM shop GROUP BY tenant_id) m
  ON m.tenant_id = s.tenant_id
WHERE s.last_seen > m.newest - 30;
```

**With the view**, you type this:

```sql
SELECT * FROM shop_current;
```

I just ran both on your real data:

```
 I typed the whole query myself | 485452
 I used the view instead        | 485452
```

Identical. The view _is_ that query — just wearing a shorter name.

## The important part: a view stores no data

This is the thing beginners usually get wrong. A view is **not** a copy of your rows.

```
 shop (real table)   | 621 MB
 shop_current (view) | 0 bytes
```

Zero. The view is a few lines of text in Postgres's catalog saying _"when someone asks for `shop_current`, run this query against `shop`."_

So:

- **No extra disk** — you're not duplicating 485,452 shops.
- **Never stale** — load new data tomorrow and `shop_current` reflects it instantly. There's nothing to refresh.
- **One place to fix** — if the 30-day rule is ever wrong, you change the view once, and every query using it is corrected.

Think of it like a saved filter in Excel. The filter doesn't copy your spreadsheet into a second file; it just decides which rows you see. Change the data, the filter shows the new result.

## Why I created these four

Your base tables hold **everything** — including the shops and routes the client stopped sending but the ML person deliberately keeps for history. That's correct and must stay.

But most of the time your app wants _only what's live today_. Before the views, every developer had to remember to write that date filter by hand — and anyone who forgot would silently show retired shops on a dashboard.

|View|Means|
|---|---|
|`shop_current`|shops the client still sends|
|`route_current`|routes the client still sends|
|`shop_route_current`|live pairs only|
|`tenant_freshness`|per-tenant summary of live vs archive|

```sql
SELECT * FROM shop;          -- everything, including history
SELECT * FROM shop_current;  -- only what's live
```

The decision is now **explicit**. You pick a name, not a filter you might forget.



Index

## 3. What an index actually is

**It's the index at the back of a book.**

Without one, to find "partitioning" you read all 400 pages. With one, you look up the word, it says _page 212_, you turn there. The book didn't get smaller — you just stopped reading all of it.

A Postgres index is a separate, sorted structure holding _just the column you search by_ plus a pointer to the full row.

Here's that difference on your `shop` table, 499,769 rows — same query, run twice, once with the index disabled:

```
WITH the index      Index Scan ... (actual rows=1)       0.084 ms
WITHOUT the index   Parallel Seq Scan on shop            92.196 ms
```

**1,100× faster.** Without the index Postgres read all 621 MB and threw away 499,768 rows to keep one. With it, it jumped straight to the row.

Notice the `rows=1` in both. Same answer. An index never changes _what_ you get — only how much work it took.
