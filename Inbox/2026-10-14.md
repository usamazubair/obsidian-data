That program can mostly only do **one calculation at a time**. So when three files arrive together, it doesn’t queue them politely one after another — it switches between all three, a bit of each, over and over.

Think of one cook with three orders. All three go on the stove straight away, so nothing is “waiting”. But the cook is now splitting attention three ways, so every dish comes out later than if it were the only order.

That’s why nobody sees “waiting in queue” — everyone sees **slow**.

### And each file is bigger than it looks

The slow part isn’t reading the Excel file. It’s the step that builds the general file: for every route, it works out every person–route combination. A 30,000-row file turns into far more rows than that in memory.

While a city is being processed, the program is holding:

- the uploaded file
- the table it read from it
- the much bigger expanded version

Three cities at once means three of those sets in memory **at the same time**, in the same program.

### So, two things slow it down

||What happens|
|---|---|
|**Sharing one worker**|Three files split the same machine’s attention|
|**Three copies in memory**|Each city’s expanded data sits there until it finishes|

### The one thing to be careful about

Because it’s all **one program**, if memory runs out, that program stops — and all three cities fail together, not just the biggest one. The portal notices and marks them failed, so nothing hangs forever, but you’d lose all three and have to re-run them.

Three cities is normally fine. It’s when someone adds a fourth and fifth at the same moment that it gets risky.

The fix, when you want it, is to run several copies of that Python program instead of one. Then three files go to three separate workers — genuinely at the same time, and one running out of memory doesn’t take the others down. It’s a change to how the program is started, not to any of the code.
